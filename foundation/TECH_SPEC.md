## 0. 阅读结论：设计文档的假设与现有资产的落差

三份文档描述的是**两件已经/将要发生的事**：

| 文档 | 角色 | 状态 |
|---|---|---|
| `idea.txt` | 玩法原始需求（9 行，无技术细节） | 已由 `DESIGN.md` 完整吸收并细化 |
| `DESIGN.md` | 前端与交互的完整设计（13 章，含验收标准） | **设计已完成，实现未开始**（工作区无 `index.html` / `app.js`） |
| `CET4.md` | 数据成果说明书，指向 `out/CET4核心2000词_词根分类.xlsx` | **数据已完成并可复现**（1998 词、260 词根、全流程脚本齐备） |

`DESIGN.md` 是按「**手工整理 20 个词缀 × 5 词 = 100 词**」（§7.1）写的，而工作区实际拥有的是**一条已经跑通的 1998 词数据流水线**。这带来 7 处必须解决的落差，它们构成本方案的编写主线：

| # | `DESIGN.md` 的假设 | 数据实测 | 影响 | 本方案对策 |
|---|---|---|---|---|
| **G1** | 词缀含**前缀/后缀/词根**三类（§7.1 `type` 字段） | `roots_canonical.tsv` 明确「前缀、后缀不算词根」，**只产出词根**，无 `type` 维度 | 词缀面板无法显示类型徽标；产品名不副实 | §3.3 新建前后缀资源表，补齐第三维度 |
| **G2** | 一个词缀 5 个词，一页 = 一个词缀 | 260 个词根规模极不均：**57 个只带 1 词、59 个带 2 词**，最大 `sist` 带 **38 词** | 「一页一词缀、固定 5 词」不成立 | §3.2 引入**学习单元（Unit）**层 + 合并/拆分算法 |
| **G3** | 词缀组覆盖全部单词 | **847 词（42%）无词根**，其中仅 46% 能被前后缀规则命中 | 42% 的词无处安放 | §3.4 词缀维度覆盖后，**511 个基础词**明确移出词缀模式 |
| **G4** | `breakdown` 助记字段手工撰写 | 仅 **43 词**有批注（多词根词），其余为空 | 卡片背面大面积空白 | §3.5 四级 breakdown 生成策略（规则命中 **81.1%**） |
| **G5** | 释义卡背面有 `example` / `exampleZh` 例句 | 数据中**完全没有例句字段** | 卡片背面缺一半内容 | §3.6 例句降级为 MVP 非目标，列入增量标注任务 |
| **G6** | 数据手写在 `data/words.js` 里 | 数据是 TSV，且有完整构建管线；且**6 词缺释义、133 词缺音标** | 需要 TSV → JS 的确定性生成器与字段容错 | §3.7 生成式构建 + §3.8 数据校验 |
| **G7** | 数据量 100 词 | 可用词 1487 词，约为设计的 **15 倍** | v1.0 据此担心 `words.js` 体积，**实测后证伪**：最大 172KB / 最小 77KB，体积不是瓶颈 | §3.7 改用实测数据；真正的问题转入 G8 |
| **G8** | 未定义兼容性与屏幕基线 | 目标机器多为 **Win7 / 集显 / 2GB 内存**的存量机，可视高度常只有 **400~600px**；v1.0 的「面板 280px + 5×200px 卡片」需 **1280px 以上**才放得下 | 不处理会直接出现「老电脑挤压溢出」与「旧浏览器白屏」 | **§4.8 兼容性与轻量化实现规范**，并协同修订 `DESIGN.md` §4.2 / §5.6 / §10 / §14 |

**一句话结论**：`DESIGN.md` 的交互设计可以**原样采纳**（状态机、翻卡状态表、取词游标、验收标准均自洽且优秀），需要改写的是**它下面的数据层**——把「手写 100 词的词缀数组」换成「由现有 1998 词流水线自动生成的学习单元流」。

| 约束 | 出处 | 技术后果 |

## 3. 数据层设计（本方案的核心）

### 3.1 学习单元 Unit 模型

`DESIGN.md` §7.1 的实体是「词缀 + 它的词」，但 G2 证明词根规模不支持这个粒度。因此引入 **Unit（学习单元）**：**Unit 是"一个词缀面板 + 一组同族词"的最小可展示组合**，一页对应一个 Unit 或 Unit 的一个片段。

```ts
Unit = {
  id: string,              // "root:sist" | "pre:re" | "suf:tion" | "mix:007"
  kind: "root"|"prefix"|"suffix"|"mix",   // mix = 微小词根合并组
  affixes: [{              // 面板内容，1 个或（mix 时）2~4 个 chip
    affix: string,         // "sist" | "re-" | "-tion"
    type:  "前缀"|"后缀"|"词根",
    meaning: string,       // "站，立"
    note: string,          // 变体说明 → "sta, stat, stit"
  }],
  words: Word[],           // 同族词，≥1
  size: number,            // words.length，供排序与分页
  tier1Ratio: number       // words 中 tier==1 的占比，供排序
}

Word = {
  id: string,              // 卡片键用 `${unitId}#${word}`，避免跨单元同词冲突
  word: string, phonetic: string, pos: string, meaning: string,
  breakdown: string,       // 见 §3.5
  tier: "1"|"2"
}
```

对应 TSV（`data/units.tsv`，供人工抽查与 diff）：

```
unitId	kind	affixes	word	phonetic	pos	meaning	breakdown	tier
root:sist	root	sist|词根|站，立|sta, stat, stit	assist	əˈsist	v.帮助，协助	sist(站) → 站在旁边 → 帮助	1
```

### 3.2 Unit Builder：分组算法（对应 G2）

**三级策略**，全部确定性、可复现：

```
输入：final_words.tsv（1998）+ roots_canonical.tsv（306）+ affixes_canonical.tsv（新增）

① 归类（每个词恰好进一个桶，优先级从上到下）
   1. root 桶：word.root 非空            → 桶键 root:<root>
   2. prefix 桶：无 root，词首匹配前缀表  → 桶键 pre:<affix>   （要求剩余长度 ≥3）
   3. suffix 桶：无 root，词尾匹配后缀表  → 桶键 suf:<affix>   （要求剩余长度 ≥3，长后缀优先）
   4. 其余 → base 池（基础词，不进词缀模式）

② 拆分大桶（桶内 ≥7 词）
   按 (tier 升序, 词长升序, 字母序) 排序后切成 5 词/片；
   末片若仅 1 词，则与前一片再对半（避免孤页）。
   → 一个桶产出多个 Unit，id 加后缀 #2 #3

③ 合并小桶（桶内 ≤2 词）
   按「相同 kind 优先、相邻字母序」把连续小桶打包成 Unit，
   每组 ≤4 个 affix chip 且 ≤5 词 → kind="mix"，面板并排显示多个词根/词缀
   剩余不足 3 词的 mix Unit 送入 base 池（不硬凑）

④ 排序（决定用户先学到什么）
   主序：tier1Ratio 降序（高频词优先）
   次序：size 降序（同族词多的先学，教学完整）
   末序：unitId 字母序（保证确定性）
   收益：用户前 20 页即覆盖最高频词根；同族 38 词的 sist 被拆成 8 片但集中在高优先级区
```

**在真实数据上的实测结果**（探针实测，复现方式见附录 A）：

| 指标 | 实测值 |
|---|---|
| 可用词（进入词缀模式） | **1487** / 1998 |
| 基础词（移出，见 §3.4） | 511 |
| 词缀模式下 Unit 数 | **312**（词根 260 + 后缀 31 + 前缀 21） |
| 其中 ≥5 词 | 111 |
| 其中 ≤2 词（进入合并，132 个 Unit / 198 词） | 132 |
| 其中 >6 词（需要拆分，最大 38 词） | 66 |
| 展平后流长度 | 1487 词 ≈ **298 页**（5 词/页） |
| 可用词的 tier-1 占比 | 46% |

> 上表的 1487 词为**归类阶段**的口径；第 ③ 步合并微小桶时会有少量（预计 <30 词）凑不足组的词移入 base 池，最终数字由 M0 构建固化。
>
> **工程含义**：约 300 页的内容规模，对一个「一次只渲染当前页、数据一次性加载」的纯前端应用是**轻量级**的，不构成性能风险（见 §4.6）。

### 3.3 词缀资源表：补齐「前缀/后缀」维度（对应 G1）

新建 `data/affixes_canonical.tsv`，沿用既有 TSV 风格（制表符分隔、`#` 注释行、无表头），在第 3 列补充「类型」，第 4 列复用「变体/说明」语义：

```
# 格式：词缀 <TAB> 中文含义 <TAB> 类型 <TAB> 说明
un	不，非，相反	前缀	加在形容词/动词前
re	再，重新；向后	前缀	置动词、名词前
-tion	名词后缀	后缀	动词→名词，表行为或结果
-able	可…的，能…的	后缀	动词→形容词
```

- 规模可控：**前缀 30~40 条 + 后缀 30~40 条**（约 70 行），是**一次性人工审定**的工作，不是逐词标注。
- 与词根表职责分离：词根表管「同族聚合」，词缀表管「构词解释 + 覆盖无词根词」。
- 前后缀匹配须**保守**（词干剩余长度 ≥3 才命中），宁可不命中进基础词池，也不要产出错误拆分（如 `in-` 误吃 `interest`）。

### 3.4 无词根词的归属决策（对应 G3）

847 个无词根词，按当前词缀表探针结果分两段：

| 分区 | 词数 | 处理 | 理由 |
|---|---|---|---|
| 词缀可解释 | 336（前缀表扩表后可达 **390**） | 进 prefix/suffix 桶，正常教学 | 有构词逻辑可讲，符合产品核心价值 |
| 纯基础词 | 511（如 `abandon, aboard, achieve, bargain, beast…`） | **不进词缀模式**，进入 `base` 池 | 无词缀可讲，强行入组会摧毁"看词缀→猜词意"的教学闭环 |

`base` 池的处置（**待决策 D-03**）：
- **推荐**：MVP 不呈现，仅在完成页显示「还有 511 个基础词，将在后续版本以『基础词表』模式提供」——诚实告知，且不污染主玩法。
- 备选：以 `mix` Unit 形式插入流尾（面板显示"本组为无词缀基础词"），代价是磨掉产品特色。

### 3.5 `breakdown` 助记串生成（对应 G4）

四级策略，按优先级降级，**绝不臆造词源**：

| 级别 | 数据来源 | 覆盖量 | 输出示例 |
|---|---|---|---|
| L1 | `final_words.tsv` 既有 `note`（43 词，多词根词） | 43 | `arch(首领)+tect(覆盖)，首领造屋者→建筑师` |
| L2 | 规则生成：**前缀剥离 + 词根变体在拼写中的定位** | 最长可达 933 词 | `re(再)+view(看)+… → 再看一遍 → 复习` |
| L3 | 批量标注（复用既有分片-子代理-合并管线，见 §3.6） | 按需 | 为 218 个「拼写与词根不直接对应」的词（`ability↔hab`、`advice↔vid`）补写 |
| L4 | 降级 | 兜底 | `该词暂无助记`（`DESIGN.md` §11 情况 9 已定义此行为） |

**L2 的可行性已验证**：1151 个带词根词中，**933 词（81.1%）的拼写直接包含词根或其变体**（变体取自 `roots_canonical.tsv` 第 3 列，如 `sist: sta, stat, stit`、`spec: spect, spic`、`ten/tain`）。算法：

```
gen_breakdown(word, root, variants, prefix):
  hit = 最长匹配的 (变体, 在词中的位置区间)     # 贪婪 + 最长优先
  if not hit: return L3/L4
  prefix_part = word[:hit.start] 若命中前缀表，否则 ""
  return "{prefix}({前缀义}) + {变体}({词根义}) → {释义的精简} → {word}"
```

**已知质量风险**：词根拼写匹配率 81% 不等于**语义**匹配率——`return` 被标注词根 `tort(扭)`、`remind` 被标注 `memor`，属于历史词源层面的正确但直觉上突兀。因此 L2 产出的 `breakdown` 必须**人工抽检 50 条**（验收项见 §7.1），抽检不通过的词降级为 L4，不硬套。

### 3.6 字段缺口补齐（对应 G6）

| 缺口 | 数量 | 处理 |
|---|---|---|
| 缺释义 | **6** 词：`sphere, sponsor, spontaneous, spouse, spray, stake` | 全部属于 S 段（`web_fetch` 截断区）。从前缀 `data/_raw/` 的既有词表回填（`fill_phonetic.py` 同款模式）；回填不到则人工补一版，这是产品最小可用度的硬门槛（卡片无释义务必堵住） |
| 缺音标 | 133 词（1865/1998） | **不猜、留空**（`CET4.md` 既定原则）。前端容错：无音标时隐藏音标行，不显示 `/  /` 空壳 |
| 缺例句 | 1487 词（全缺） | MVP 非目标，释义卡背面改为「词根拆分 + 词性 + 多义项」；例句作为 M4 增量（见 §6） |
| 词性 `pos` | 无独立列 | 从 `meaning` 前缀正则解析：`^(vt|vi|v|n|a|adj|ad|adv|prep|conj|int|pron|num)\.`，实测覆盖率 **1979/1998（99.0%）**，19 词无词性标记时 `pos=""` 并原样显示释义 |

### 3.7 运行期数据产物与体积（对应 G7，**v1.1 已改为实测**）

```js
// data/words.js —— 由 scripts/build_web_data.py 生成，人工不手改
window.CET4_META = { version:"1.0", built:"2026-…", words:1487, units:312, base:511 };
window.CET4_UNITS = [ /* Unit[]，按 §3.2 ④ 排序 */ ];
```

**三种候选形态的真实体积**（对当前 1487 词的同一份数据实测，UTF-8 字节）：

| 形态 | 体积 | 评价 |
|---|---|---|
| 长字段名结构化 JSON（`word`/`phonetic`/`meaning`/`breakdown`/`tier`） | **172 KB** | 可读性最好，便于在浏览器里直接排查 |
| **短字段名 JSON（`w`/`p`/`m`/`b`/`t`）** | **104 KB** | **采用**：无自定义解析、无分隔符风险，体积已足够小 |
| 紧凑字符串（行 + `\|` + `~` 分隔，运行时 `split` 解析） | **77 KB** | 仅比短字段名省 27KB，却引入自定义解析与分隔符转义风险 → **不设为默认**，保留为 `--format=compact` 可选开关 |
| （参考）紧凑串 gzip 后 | 37 KB | `file://` 下无法依赖 gzip，仅供参考 |

> **v1.0 的 350KB 估计被实测证伪**（高估约 2~4.5 倍）。结论随之改变：**数据体积不是本项目的瓶颈**，
> 不需要为此牺牲可维护性。因此默认采用**短字段名 JSON**，运行期由 `app.js` 的 `denormalize()` 还原字段名；
> 词性 `pos` 不落盘，运行期由 `meaning` 解析（§3.6）。
> 若某天扩到全四级 4600 词（约 3 倍 → 约 310KB），再启用 `--format=compact` 或按 Unit 分片
> （预留 `CET4_META.shards` 字段），**现在不必提前复杂化**。

**为什么不用紧凑串做默认**（实测发现的风险）：探针在字段中检出 **99 条释义含 ASCII 分号 `;`、2 条音标含 `;`**
（如 `n.权利; 权力` 一类的混排），因此分号不能作为分隔符；改用 `|` 与 `~` 后当前数据无冲突，
但这属于**「今天恰好没冲突」**——一旦后续回填的释义或例句里出现 `|`，产物会静默错行。
JSON 自带转义、天然免疫该风险，这也正是默认选它的第二个理由。若启用 compact 模式，构建必须执行 §3.8 断言 8。

### 3.8 数据契约与自检

`scripts/check_web_data.py` 断言清单（任一失败即构建失败，防止脏数据进前端）：

1. `words.js` 中词总数 = `final_words.tsv` 中可用词数（1487 ± 已知白名单）。
2. 每个 Unit 的 `words` 非空；`affixes` 非空；`kind` 合法。
3. 无重复卡片键 `${unitId}#${word}`；**全局无重复单词**（防止「添加单词」后语义重复）。
4. 每个 `affix` 都能在 `roots_canonical.tsv` 或 `affixes_canonical.tsv` 中查到（沿用 `audit_roots.py` 的重名/非标准写法检查思路）。
5. 每个词 `meaning` 非空 **或** 在已知 6 词白名单内（见 §3.6）。
6. 无 `breakdown` 为空串（允许为 L4 的「该词暂无助记」）。
7. 排序稳定性：两次构建产出字节一致（确定性构建）。
8. **分隔符安全（仅 compact 模式）**：断言任一字段都不含 `|`、`~`、`\n`；命中即构建失败（实测背景见 §3.7）。
9. **体积门限**：`words.js` ≤ 250KB、单文件便携版 ≤ 500KB；超出即报警（防后续扩量时无声膨胀）。
10. **零外部引用**：`index.html` / `styles.css` / `app.js` 中不得出现 `http://` / `https://` / `//cdn` 等外链（保证断网与 `file://` 可用）。

### 4.2 状态机

完全采纳 `DESIGN.md` §3 的四态机与三态入口判断，子状态定义如下（`cardState` 沿用其 §7.2 定义，新增 `unitPanelState` 以支撑 G2 的 mix Unit）：

```
learning 子状态：

```

主界面三态按钮文案、跨天归档、游标前进语义**全部照搬** `DESIGN.md` §3 / §7.4，不改设计。

### 4.3 取词与分页（`DESIGN.md` §6 原样保留，仅换数据源）

`DESIGN.md` §6 的 `takeWords(count)` + `groupByAffix()` 是正确解法，**唯一要改的是流从哪里来**：

```js
// 旧：AFFIXES.flatMap(a => a.words.map(...))
// 新：UNIT_STREAM —— 构建期由 build_units.py 按 §3.2 排好序展平
const UNIT_STREAM = CET4_UNITS.flatMap(u =>
  u.words.map(w => ({ unitId: u.id, wordId: w.id }))
);

function takeWords(count) {
  const start = loadCursor();                       // cet4.cursor.v1
  const slice = UNIT_STREAM.slice(start, start + count);
  saveCursor(start + slice.length);
  return groupByUnit(slice);                        // 相邻同 unitId 合并成一页
}
```

**页面→面板的映射**（新增逻辑，对应 mix Unit）：

```js
function panelFor(page) {
  const unit = UNIT_BY_ID[page.unitId];
  if (unit.kind !== "mix") return unit.affixes;        // 普通页：单个 chip
  // 混合页：只显示「本页实际出现词所属」的 chip，避免面板出现与卡片无关的词根
  const shown = new Set(page.words.map(w => w.affixKey));
  return unit.affixes.filter(a => shown.has(a.affix));
}
```

其余规则照搬：游标只前进不回退、「添加单词」天然续接不重复、`groupByUnit` 只合并相邻同 Unit（`DESIGN.md` §6.2）。

### 4.4 持久化

`DESIGN.md` §7.2–7.4 的三个键与场次自包含设计**原样采用**，仅把 `affixId` 字段更名 `unitId`、`pages[].wordIds` 不变，并加 `schema` 版本号：

| 键 | 内容 | 变更 |
|---|---|---|
| `cet4.cursor.v1` | 全局取词游标 | 不变 |
| `cet4.session.v1` | 今日场次（自包含 pages + cardState） | `affixId` → `unitId`；新增 `schema: 1` |
| `cet4.history.v1` | 历史归档 | 不变 |
| `cet4.meta.v1` | 新增：`{ dataVersion }`，与 `CET4_META.version` 不一致时**清游标与场次**（数据重建后游标语义会漂移，必须失效） |

**迁移策略**：`v1` 为初版，读取时若 `schema` 缺失或 `dataVersion` 不匹配 → 丢弃旧场次并提示「词库已更新，已重新开始」，**不做数据迁移**（成本收益不成立）。

### 4.5 交互与样式要点（对齐 `DESIGN.md` §5 / §10）

- 顶部栏保留「上一组」按钮（`DESIGN.md` §11 #7 的容错建议，采纳）。
- 卡片三态 `hidden/front/back` 与点击行为表（§5.2）**逐行实现，不加戏**；`flipped` 一经置 true 永久保留（仅统计用）。
- 词缀面板：普通 Unit 显示 1 个 chip（词缀 + 类型徽标 + 含义 + 说明）；**mix Unit 显示 2–4 个小 chip 并排**，chip 数量自适应换行。

- 窄屏 <768px：词缀面板顶部折叠 + 单词卡竖排 + 释义卡**跟随被点击卡片**（`DESIGN.md` §4.2 的理由成立，保留）。
- 无障碍：卡片用 `<button>`、`aria-pressed` 标记翻面、保留焦点环。

### 4.6 性能预算（v1.1 按实测修正）

**目标机器是 2GB 内存、集显、机械硬盘的存量机**，因此预算按「最慢机器」定，而不是按开发机：

| 项 | 预算 | 依据 |
|---|---|---|
| `words.js` 体积 | **≤ 120 KB**（实测 104 KB） | §3.7 实测；v1.0 的 400KB 预算过宽 |
| 整站总载荷（html+css+js+数据） | **< 200 KB** | 零字体、零图片、零 CDN |
| 首个可交互 | **< 200 ms**（本地 `file://`，机械盘） | 无框架启动、无网络等待；一次 `<script>` 解析 |
| 数据解析（JSON.parse） | **< 10 ms** | 104 KB 纯文本 |
| 页面内存占用 | **< 50 MB** | 约 1487 个小对象 + 少量 DOM，远低于预算 |
| 每页 DOM 节点 | **< 200** | 只渲染当前页 5 张卡 + 面板 |
| 换页渲染 | **< 30 ms** | 单次 DOM 重建；**仅换页/换视图时发生** |
| 翻卡（点卡） | **无重排、无重绘** | 只切类名 + `transform`/`opacity` 过渡（§4.8） |
| 动画帧率 | 集显下 ≥ 30fps | 只做合成层动画，不碰 `width`/`height`/`box-shadow` |

> 关键结论：**运行时成本与总词数几乎无关**（`takeWords` 只切片、`render` 只画当前页 5 张卡），
> 所以「全量 1487 词」在低端机上与「100 词原型」的开销几乎一致——**规模不是风险**。

### 4.7 为什么全量 1487 词可以直接进 MVP

`DESIGN.md` §7.1 建议「先用 100 词跑通交互」，其动机是**手写数据的成本**。本方案的数据是自动生成的，该动机消失；而运行时成本与总词数几乎无关（`takeWords` 只切片、`render` 只画当前页）。因此建议 MVP 直接全量上线，避免二次数据工程。

### 4.8 兼容性与轻量化实现规范（v1.1 新增，落地 `DESIGN.md` §14）

#### 4.8.1 语法白名单（构建期自动守卫）

`app.js` **只允许 ES5**。新增 `scripts/check_es5.py`（纯正则，≤60 行）扫描 `app.js`，命中即构建失败：

| 禁止 | 正则/判定 | 替代写法 |
|---|---|---|
| 箭头函数 | `=>` | `function (x) { … }` |
| `let` / `const` | `\b(let|const)\s` | `var` |
| 模板字符串 | 反引号 `` ` `` | `'a' + b + 'c'` |
| `class` / `extends` | `\bclass\s+\w` | 构造函数 + 原型（本项目其实只需普通对象） |
| 展开/剩余 | `\.\.\.` | `apply` / 显式参数 |
| 解构 | `{\s*\w+\s*}\s*=`、`\[\s*\w+\s*\]\s*=` | 逐字段赋值 |
| 默认参数 | `function\s*\([^)]*=` | 函数体内 `if (x === undefined) x = …` |
| 新增数组/字符串方法 | `.includes(`、`.padStart(`、`.padEnd(`、`Object.entries(`、`Array.from(`、`Object.assign(` | `indexOf(...) !== -1`、手写补零、`Object.keys` + 循环 |
| CSS 禁用特性 | `var(--`、`display:\s*grid`、`gap:`、`clamp(`、`backdrop-filter` | 字面量、flex + margin、长度分档字号、纯色 |

> 这条守卫把「我们承诺兼容老浏览器」从口头约定变成**机器可验证的断言**，成本约 40 行 Python。

#### 4.8.2 能力探测与降级阶梯（初始 ≤20 行 JS）

启动时检测一次，把结果挂到 `<body>` 类名，CSS/JS 单向分支（对应 `DESIGN.md` §14.4）：

```
detect() 依次判断：
  1. ES5 环境可用？     → 否则 body.noes5：只渲染静态升级提示（此判断必须在 ES5 里做，否则旧浏览器解析期即失败）
  2. 支持 3D 翻面？      → 否则 body.no3d：翻卡改淡入切换（DESIGN.md §5.6 B 级）
  3. prefers-reduced-motion / hardwareConcurrency ≤ 2？ → body.reduce / body.perf-low：去掉过渡（C 级）
  4. localStorage 可写？  → 否则 body.nostore：内存态存储 + 主界面一行提示
```

- 所有探测包在 `try/catch` 内，**任何一项探测失败都不影响其余功能**。
- `?diag=1` 打开诊断条，显示 `浏览器 / 视口 / DPR / 3D / 存储`，便于在用户机器上远程定位问题（无需 F12）。

#### 4.8.3 渲染作用域：局部更新优先（重要轻量化点）

`DESIGN.md` §8 的「每次状态变更后整体重建 DOM」在正确性上没问题，但在**弱 CPU** 上每次点卡都重建整页会产生
无谓的解析、布局与垃圾回收压力。因此细化为**按变更范围选择渲染粒度**：

| 变更 | 渲染范围 | 说明 |
|---|---|---|
| 点卡（显示释义卡 / 翻面 / 换个词看） | **只切类名 + 改文本**，不重建 | 单卡级 patch，零重排 |
| 切页（下一组 / 上一组） | 仅重建**卡片区 + 面板**，顶部栏与底栏复用 | 一次重建，页面骨架不动 |
| 切视图（home / countSelect / learning / complete） | 整体重建 | 频率最低，成本可忽略 |
| 计时器每秒刷新 | **只改一个文本节点** | 绝不用 `innerHTML` 重建顶部栏（否则每秒重排） |

实现上仍只保留**一个 `render(state)` 入口**（可维护性不变），但内部按上述粒度分派；卡片元素以 `${unitId}#${word}` 缓存引用于 `state.dom`。

#### 4.8.4 单文件便携版构建

`scripts/build_single_file.py`：读取 `index.html`，把 `<link rel="stylesheet">` 替换为 `<style>`、
两个 `<script src>` 替换为内联 `<script>`，输出 `build/CET4翻卡记忆_单文件版.html`。

- 目的：现实中用户会拷贝**一个文件**，而不会正确拷贝整个目录（`DESIGN.md` §14.6）。
- 顺带消灭一切路径问题：不依赖相对路径、不受中文/空格路径影响、不触发任何 `file://` 资源加载限制。
- 校验：产物中不得残留任何 `src=` / `href=` 指向本地文件的引用（§3.8 断言 10 同款检查）。

### 附录 A.2　体积与分隔符实测（v1.1 新增）

对同一份 1487 词数据、同一次分组结果（312 个 Unit）实测，UTF-8 字节：

| 形态 | 体积 | 备注 |
|---|---|---|
| 长字段名结构化 JSON | 172 KB | 可读性最好 |
| **短字段名 JSON** | **104 KB** | **采用为默认**（无自定义解析、无转义风险） |
| 紧凑字符串（`\|` + `~` 分隔） | 77 KB | 仅省 27KB，降为可选开关 |
| 紧凑串 gzip | 37 KB | `file://` 下不可依赖，仅参考 |

**为什么 v1.0 的 350KB 估计是错的**：v1.0 按「每条记录含全部字段的可见字符数」粗估，未扣除实际数据里释义普遍偏短、
且重复词根含义只在 Unit 头出现一次。实测 172KB（最啰嗦形态）即为其估计值的 **1/2**，短字段名形态则为 **1/3.4**。

**分隔符安全实测（重要）**：

| 分隔符候选 | 冲突数 | 结论 |
|---|---|---|
| ASCII 分号 `;` | **释义 99 条 + 音标 2 条含 `;`** | **不可用作分隔符** |
| 全角分号 `；` | 释文中 1163 条 | 是数据本身的义项分隔符，保留 |
| 竖线 `\|` / 波浪号 `~` / 制表符 | 0 | 当前可用，但**必须由构建断言守住**（§3.8 断言 8） |

> 这条实测直接改变了 D-10 的结论：**自定义分隔格式的隐性风险高于它的收益**，因此默认改用 JSON。
> 复现方式：读 `final_words.tsv`，对每个字段统计候选分隔符出现次数。
